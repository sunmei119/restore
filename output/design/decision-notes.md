# Decision Notes（design）

基准：align（`output/align/align.md`）。本文件记录相对上游基准的关键决策，按四类分节。

## 设计决策

- **角色更名**：「租户管理员」统一更名为「机构管理员」（界面展示名与文档表述）；内部角色标识 `tenant_admin`、层级「租户」同步调整为「机构」，数据范围「本租户」调整为「本机构」。
- **审核职责收归桂教通超级管理员**：应用上线申请审核仅由 `platform_admin` 执行；机构管理员、教职工移除「应用审核管理」模块（P10/P11/P11v）；平台运营员（`platform_operator`）不再承担审核职责，角色定位调整为「巡检应用、处理工单、配置教育服务中心上架」。
- **审核通过后进入上架列表**：机构管理员新增应用提交上线申请后，由桂教通超级管理员审核；审核通过后应用进入机构管理员的应用上架管理列表（P04），状态为未上架（`listing_status = unlisted`），由机构管理员再执行上架配置（P05）后才对范围可见。
- **原型交互同步**：P10 菜单对机构管理员隐藏（仅超管可见）；审核通过时应用写入上架列表（未上架）并移入已审批列表，toast 提示「审核通过，应用已进入机构管理员上架列表（未上架）」。
- **套餐配置调整**：P26 应用套餐配置移除「启用/停用」功能及 `is_active` 字段；删除套餐前校验使用状态，被使用（订单套餐授权、订单接收记录、试用套餐记录、基座套餐关联、应用上架配置引用）不可删除并提示，未被使用弹窗二次确认后删除。
- **授权套餐多选与购买详情套餐联动**：P02 上线申请「授权套餐」支持下拉多选并增加可选套餐数据；P22 应用详情/购买视图付费应用展示多个授权套餐卡片，点击切换套餐联动展示价格，「立即购买」按钮展示所选套餐价格，购买页商品单价/实付按所选套餐计算。
- **上架范围动态引用规则**：应用上架范围解析出的机构集合为每次实时解析（动态引用，非上架时刻快照）；机构、标签、范围任一环节增删，已上架应用上架范围自动同步更新（标签增删机构 → 引用该标签的范围自动同步 → 使用该范围的应用上架范围同步），无需重新上架/审核；被范围引用的标签、被应用上架范围引用的范围不可删除；标签/范围内移除机构仅缩小上架范围，应用上架状态不变，范围外机构不可见、已安装应用不卸载。
- **术语统一**：「租户」全文统一为「机构」（含数据字典字段含义、统计口径等所有正文表述）；align 基准保留上游"租户"原词；内部标识符 `tenant_*` 保留原名。
- **P17 应用统计看板双角色口径**：平台角色（platform_admin / platform_operator）统计全平台数据；机构管理员（tenant_admin）可访问并统计本机构数据。机构管理员维度：应用安装数（本机构范围内累计）、机构应用数（本机构上架应用数）、活跃应用数、应用使用人数（均限本机构范围）；图表与排行数据范围随角色切换；导出仅限本机构范围。
- **P17 导出文件清单与字段定义**：导出为 1 个 Excel 文件（.xlsx），内含 6 张工作表——统计概览、应用安装统计、应用使用统计、应用分类统计、用户数量榜 Top10、应用安装排行榜 Top10，字段与页面各统计区块一一对应；数据范围按角色（超管全平台/机构管理员本机构范围）、时间范围与页面当前选择一致、文件名「应用统计_YYYY-MM-DD.xlsx」、需具备查看权限方可导出。
- **P17 统计数据实时性与刷新频率**：采用"实时 + 准实时（分钟级）"混合模式，不做 T+1。实时指标（秒级）：应用安装数、平台应用数/机构应用数、应用分类统计、活跃/非活跃应用占比（基于基础业务表实时聚合）；准实时指标（最长延迟 5 分钟）：应用点击量趋势、应用使用人数、活跃应用数、用户数量榜 Top10、应用安装排行榜 Top10（行为流水 5 分钟粒度汇总落库）。刷新时机：进入页面、切换时间范围/角色时实时拉取，提供手动「刷新」按钮，不做自动轮询；历史周期（本周/本月/本年）由日汇总表累加，已结算日期数据固定。理由：纯 T+1 与"今日 0:00~当前时间"口径冲突（今日周期将无当日数据），纯实时对行为流水全量扫描性能不可控，混合模式兼顾实时性与查询性能。
- **P18 授权状态新增「授权失败」与手动授权兜底**：授权状态由两种扩展为三种（授权成功/未授权/授权失败，失败标签红色 danger，数据字典 `auth.status` 枚举增加 `failed`）。自动授权失败的订单进入「授权失败」状态，授权状态描述记录失败原因；操作列在授权方式=自动且状态=失败时显示「手动授权」按钮，点击弹窗二次确认「自动授权失败，确认手动授权【套餐名称】吗？」，确认后授权成功、状态变为授权成功、描述变为已手动授权、toast「手动授权成功」。理由：自动授权失败若无兜底将永久处于未授权状态，复用现有手动授权能力提供恢复路径，避免用户套餐不可用。
- **P26 被引用套餐编辑约束**：套餐被引用（订单套餐授权/订单记录/试用套餐记录/其他套餐基座关联/应用上架配置引用）时仍允许编辑，但编辑仅影响新购——保存后仅对之后新产生的订单/授权/试用按新配置生效；历史订单沿用下单时的套餐快照（下单时套餐名称、价格、分配大小、计量单位、有效期等已快照至订单），不受后续编辑影响；应用上架配置引用的授权/试用套餐同样仅对新购生效。理由：套餐配置会被授权/订单长期引用，若编辑联动历史数据将导致已售出套餐权益变更、对账混乱，快照隔离保证历史订单权益不变，删除保护（被使用不可删除）与编辑放开形成"可改不可删、改不动历史"的约束组合。
- **P19 订单记录范围定义**：订单记录管理记录两类订单——①在桂教通平台购买的付费应用订单（教育服务中心/我的应用中心内嵌商城商品页下单）；②通过商城下单的订单（商城嵌入式页面/无痕下单）。理由：align 基准将教育服务中心定位为"应用购买（嵌入式商城页面/无痕下单）"，付费应用订单存在平台内嵌商城与商城两个下单入口，订单接收记录需统一汇总两类订单，便于平台管理员跟踪、对账。
- **P22 支付结果同步机制（PC 端同步提示）**：采用"惠缴费支付回调 + PC 端轮询"组合，不做 WebSocket/SSE 服务端推送。惠缴费完成支付后异步回调平台后端（回调含签名校验、幂等处理），后端更新订单状态为已支付并触发订单记录、套餐授权、接收记录生成；PC 端支付界面每 3 秒轮询一次订单支付状态接口，检测到已支付即停止轮询并同步提示"支付成功"、进入成功页，检测到失败提示失败并展示"返回订单"按钮，超过支付有效期（15 分钟，与二维码有效期一致）未支付提示支付超时、二维码失效可点击"刷新二维码"。理由：惠缴费回调只能到达后端、无法直达浏览器；扫码支付场景页面长期停留、状态变化低频，3 秒轮询实现简单可靠且足够及时，引入 WebSocket/SSE 长连接组件复杂度高、收益低。
- **5.3 字段级权限例外补齐 P02/P02b/P05**：字段级权限例外由 P11/P17/P08 扩展至 P02 应用申请编辑页、P02b 应用详情-上线配置、P05 应用上架配置页。P02：应用类型字段仅桂教通超级管理员展示且必填（机构管理员不展示、默认非平台应用）；上线配置的跨机构层级、所属机构仅超管且低代码应用展示（仅是否跨机构=是时显示），机构管理员不展示这两项。P05：范围选择按角色与是否跨机构联动（学校机构管理员不展示、默认本校），分享范围仅机构管理员展示（学校机构必填，被分享应用不展示）。理由：P02/P05 的角色条件字段原散落于页面正文各表，权限评审与实现对照时易遗漏，集中到 5.3 形成完整字段级权限清单；纯字段间业务联动（推送地址随数据同步、suiteID 随生态应用、可见性地址随打开方式等）不属于角色权限差异，仅作排除说明，避免 5.3 与页面联动规则重复。
- **P02b 所属机构交互升级（可搜索多选输入框）**：所属机构由"下拉选择（支持搜索）+ 添加按钮 + 机构选择弹窗"改为可搜索多选输入框——输入机构名称模糊搜索（最多查询 50 条），支持多选；数据来源按跨机构层级获取：层级为厅→所有教育行政部门、市→所有市级教育行政部门、区县→所有区县教育行政部门；跨机构层级切换时清空已选并重新加载候选。理由：原弹窗方案（≤10 列表点击回填、>10 下拉选择）为临时交互，跨机构层级下机构数量大（区县数百个），弹窗列表/下拉无法高效定位；搜索输入框与 P05 分享范围"其他机构"多选框交互一致，模糊搜索+多选满足批量选择，50 条上限防止候选过多影响渲染。
- **超管操作权限补充（P01/P02/P04/P04b/P05）**：桂教通超级管理员对应用申请管理页、应用申请编辑页、应用上架管理页、应用安装列表页、上架范围配置页全部可操作（全平台，含新增/管理/上线/下线、保存/提交、上架/下架/安装、安装/卸载、上架配置）；默认权限规则中超管列由「全部只读」/「—」改为「全部管理」，与原型按钮展示及 PRD 5.2 一致。理由：超管承担全平台应用治理职责，对应用生命周期操作需直接可操作；原「全部只读」仅允许查看，与原型行内操作按钮展示冲突。
- **P05 全平台提示文案补全「自动安装」语义**：原型 P05 范围选择「全平台」文本提示，机构管理员由"上架到当前机构及所有下级机构"补全为"上架到当前机构及所有下级机构，并自动安装到应用中心"，与 P05 表格「— 范围补充 - 全平台」备注（全平台=上架到当前机构及所有下级机构并自动安装到应用中心）一致；超管提示保持"全平台指的是所有机构和学校"。理由：机构管理员全平台含自动安装到应用中心语义，原型原提示遗漏；超管全平台（跨机构=否时可选）上架后不自动安装，仅跨机构=是时自动安装到范围内机构应用中心，故超管提示不追加自动安装，避免与上架行为矛盾。
- **P04 补充「已下架」演示数据并实现重上架范围回填**：原型 P04 应用上架管理列表原无 dismissed 示例数据，下架→重上架链路无法演示；补充演示应用「考试管理」（appList 与 shelfList 各一条，dismissed 状态、上架范围=南宁市教育局），同步修正 P01 分页条数（8→9 条，修正既有 10 条笔误）与 P04 分页条数（→12 条）。同时补齐本文件 P04 已定义但原型缺失的 dismissed 重上架默认回填下架前上架范围的实现（P05 进入时 scopeType=zone、selectedZones 回填原范围）。理由：补数据后链路可完整演示；若不实现回填，重上架演示时范围将默认全平台/当前机构及所有下级机构，与「保留原上架范围」规则冲突。
- **P05 上架新增承诺书勾选（需求变更）**：原型 P05 免责声明与承诺书由"文案 + 蓝色链接"升级为"checkbox + 文案 + 蓝色链接"，未勾选时"确认上架"置灰并增加提交兜底校验；本文件 P05 流程（115 行）、P05 表格说明（504 行）、免责声明与承诺书行（507 行）、P04 状态流转表 unlisted 行限制条件（936 行）中"勾选已迁移至 P02b"的表述同步改为"P02b 与 P05 均须勾选"。理由：上架提交同样承担法律责任承诺，dismissed 重上架、P02b 审批后上架均需在上架时再次确认；与 PRD 基准保持一致。
- **P25 我的订单支付入口与商品信息（需求变更）**：原型 P25 订单列表卡片与订单详情页新增"支付"按钮（仅待支付且未超时显示），点击跳转 P22 付款界面微信扫码支付，支付成功同步订单状态；订单详情"商品套餐"区更名"商品信息"，展示风格改为与发票信息一致的标签+值网格。本文件 P25 表格（858-862 行）同步更新，新增"订单列表操作/订单详情操作"两行。理由：原型补齐设计已定义但未实现的"未支付且未超时→支付"入口，并统一商品信息展示风格；与 PRD 基准保持一致。
- **P02 新增「跳转登录限制」字段（需求新增）**：应用申请编辑页（P02）新增必填下拉字段「跳转登录限制」，枚举值为 none（无需登录）/ account_only（仅持有账号登录）/ register_or_login（可注册或登录），落点同步至 P02b 应用详情页、P05 上架配置页应用基本信息区、P11/P11v 审批信息区，数据字典新增 `app.jump_login_limit`。理由：用户明确要求在应用申请界面控制跳转登录限制，且该字段为应用可见性与接入控制的关键属性，需在申请阶段确定。
- **P02「应用类型」调整为「是否平台应用」（需求变更）**：P02 字段名由「应用类型」改为「是否平台应用」，枚举由「平台应用 / 非平台应用」改为「平台型 / 非平台型」（内部标识符 `platform` / `non_platform` 不变），默认选中非平台型；字段下方新增说明文案「平台型指的是不需要上架能用的应用，比如：桂教通门户；非平台型指的是需要上架使用的原生应用、生态应用等。」字段级权限不变：仅桂教通超级管理员展示且必填，机构管理员固定为 `non_platform`。P01/P04/P06/P10 列表列名同步改为「是否平台应用」，P04 应用分享管理筛选条件同步改为「是否平台应用（平台型/非平台型）」，数据字典 `app.app_type` 说明与必填属性同步更新。理由：用户明确指定字段名、枚举值与说明文案；原「应用类型」与「应用属性（原生应用/生态应用）」在列表中并列展示易混淆，改为「是否平台应用」后语义边界清晰。
- **P09 编辑二级分类支持变更上级分类（需求变更）**：应用分类管理页编辑二级分类时，弹窗除分类名称、排序外新增「上级分类」下拉，默认带出当前所属一级分类并允许改选其他已启用的一级分类；保存时校验所选一级分类下名称与编码不重复（排除自身），变更后自动更新 `category.parent_id` 并展开新上级。编辑一级分类不展示该字段；「添加下级分类」仍为只读上级文本。理由：用户明确要求编辑二级分类时展示并可修改上级分类；原实现二级分类挂错上级后只能删除重建，改归属需可编辑。
- **P10 审批列表列调整（需求变更）**：待审批、已审批两个 Tab 的列表均将「开发者名称」列替换为「机构名称」（`app.tenant_name`，应用所属机构），并在「应用分类」列后新增「应用属性」列（`app.type` + `app.native_type` 完整拼接，如"原生应用/低代码应用""生态应用"）。理由：审批视角需按机构维度定位申请来源，开发者个人名对审批决策无价值；应用属性是审批判断的关键依据，紧跟应用分类便于对照。原型中「是否平台应用」列保留并置于「应用属性」之后，与 P01 列表「分类→应用属性」相邻一致。
- **P01 上线驳回状态与审批信息可见性（需求变更）**：应用上线申请被驳回时 app.status 置为 `rejected`（列表状态标签显示红色「已驳回」），不再停留在「未上线」；P01 状态下拉新增「已驳回」，「上线」按钮对 offline / rejected 均显示；机构管理员点击「管理」进入 P02b 管理模式时，页面下方展示「审批信息」区（申请时间、申请人、审批人、审批时间、审批结果、审批意见），重新提交上线申请后 app.status 回到 offline（列表显示待审批），审批信息区随之隐藏。理由：驳回后若仍显示「未上线」，机构管理员无法区分从未提交与被驳回；审批意见是整改依据，需在管理入口直接可见，而不是只保留在超管审批详情里。
